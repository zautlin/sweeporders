# SweepOrders

A research pipeline that analyses ASX **Centre Point sweep order** execution
quality. It compares the way sweep orders actually executed on the lit market
against a simulation of how they would have executed in the dark pool
(midpoint matching), and produces per-order metrics plus several roll-up
reports.

The pipeline is six stages, packaged as four flat Python files:

| Files | Stages | Purpose |
|---|---|---|
| `process.py` | 1+2 | Ingest raw data, partition by `(date, orderbookid)`, simulate dark-pool matching |
| `aggregate.py` | 3+4 | Calculate ~36 metrics per order; compare real vs. simulated |
| `report.py` | 5+6 | Per-security and cross-cut reports (by day, ticker, volume bucket) |
| `run.py` | — | Convenience wrapper that runs all three in sequence |

The code is pure Python (`pandas`, `numpy`, `duckdb`, `polars`, `psutil`)
and uses `pathlib` everywhere, so it runs unchanged on **Windows**,
**macOS**, and **Linux**.

## 1. Folder structure

After cloning / unzipping the project you should have:

```
sweeporders/
├── README.md                this file
├── requirements.txt         Python dependencies
├── run.py                   one-shot orchestrator
├── eda.py                   exploratory data analysis (run before processing)
├── config.py                constants and feature flags
├── process.py               Stages 1+2
├── aggregate.py             Stages 3+4
├── report.py                Stages 5+6
├── simulator.py             numpy simulator kernel (sole Stage 2 implementation)
├── tests/                   pytest suite (parity baseline + smoke tests)
├── docs/                    spec sources
│   ├── bi.txt               ASX Centre Point behaviour spec
│   └── dd.txt               ASX Centre Point data dictionary
└── data/                    inputs and outputs (you create + populate `raw/`)
    ├── raw/                 INPUT — drop your CSV / parquet files here
    │   ├── orders/          {ticker}_{YYYYMMDD}_orders.csv
    │   ├── trades/          {ticker}_{YYYYMMDD}_trades.csv
    │   ├── nbbo/            {ticker}_{YYYYMMDD}_nbbo.csv
    │   ├── session/         {YYYYMMDD}_session.csv
    │   ├── reference/       {YYYYMMDD}_orderbook.csv
    │   └── participants/    {YYYYMMDD}_par.csv
    ├── processed/           OUTPUT of Stage 1+2 (auto-created)
    │   └── {YYYY-MM-DD}/{orderbookid}/
    │       ├── cp_orders_filtered.parquet
    │       ├── cp_trades_matched.parquet
    │       ├── orders_before_matching.parquet
    │       ├── orders_after_matching.parquet
    │       ├── last_execution_time.parquet
    │       ├── nbbo.parquet
    │       └── cp_trades_simulation.parquet
    ├── outputs/             OUTPUT of Stage 3+4 (auto-created)
    │   └── {YYYY-MM-DD}/{orderbookid}/
    │       ├── real_trade_metrics.parquet
    │       ├── simulated_trade_metrics.parquet     (only if sim produced trades)
    │       └── simulation_order_summary.parquet
    └── reports/             OUTPUT of Stage 5+6 (auto-created)
        ├── by_day.csv
        ├── by_ticker.csv
        ├── by_volume_bucket.csv
        ├── by_participant.csv      (stub — needs raw-orders join)
        ├── by_session_phase.csv    (stub — needs session join)
        └── per_security/
            └── {YYYY-MM-DD}_{orderbookid}_{ticker}.csv
```

You only ever populate `data/raw/`. Everything under `data/processed/`,
`data/outputs/`, and `data/reports/` is generated by the pipeline and can be
deleted at any time to force a clean rerun.

### Raw filename conventions

The pipeline discovers files by scanning the six raw folders. Filenames
follow these patterns; both `.csv` and `.parquet` are accepted (parquet is
preferred when both exist).

| Folder | Example filename |
|---|---|
| `orders/` | `cba_20240505_orders.csv` |
| `trades/` | `cba_20240505_trades.csv` |
| `nbbo/` | `cba_20240505_nbbo.csv` |
| `session/` | `20240505_session.csv` |
| `reference/` | `20240505_orderbook.csv` |
| `participants/` | `20240505_par.csv` |

The trade-date inside the file may differ from the date label in the
filename — the pipeline always partitions by the **actual timestamp**, not
the filename, so your folder names under `data/processed/` may not match
the raw filename's date.

## 2. Prerequisites

* **Python 3.10 or newer** (the pipeline targets 3.10; 3.11 / 3.12 also work).
* About 2 GB of free disk per ticker-day for outputs.
* No native compilers required — every dependency ships pre-built wheels
  for Windows and macOS.

Verify Python is installed and on your path:

```
python --version
```

If `python` resolves to Python 2 on your system, use `python3` instead in
all commands below.

## 3. Setup

Pick the section that matches your operating system.

### macOS / Linux

```bash
# from the repo root
python3 -m venv swp_env
source swp_env/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
```

A pre-built helper is provided:

```bash
source activate.sh        # activates swp_env and prints versions
```

### Windows — Command Prompt (`cmd.exe`)

```bat
REM from the repo root
python -m venv swp_env
swp_env\Scripts\activate.bat
python -m pip install --upgrade pip
pip install -r requirements.txt
```

### Windows — PowerShell

```powershell
# from the repo root
python -m venv swp_env
.\swp_env\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
```

If PowerShell refuses to run `Activate.ps1` because of the execution policy,
either use Command Prompt above, or run **once per session**:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

### Verify the install

After activation, in any of the three shells:

```
python -c "import pandas, numpy, duckdb, polars, psutil; print('ok')"
```

You should see `ok`. Run the test suite to confirm everything is wired:

```
python -m pytest tests/ -q
```

83 tests should pass in roughly 3 seconds. (The byte-diff parity tests
require `tests/parity_baseline/` to be present; if it is, they auto-run.)

## 4. Drop your raw data into `data/raw/`

Two ways:

**Option A — already organised.** Copy your daily files directly into the
matching subfolder under `data/raw/{orders,trades,nbbo,session,reference,participants}/`.
Subdirectories that don't exist are auto-created the first time you run
the pipeline. CSV is read as-is via DuckDB's parallel parser; parquet
files are preferred when both formats exist for the same base name.

**Option B — let `organize_raw.py` distribute them for you.** If your
raw files are sitting flat in `data/` rather than already split into
subfolders, run:

```
python organize_raw.py
```

The script classifies each file by its filename suffix and moves it
into the right subfolder (creating subfolders as needed):

  `*_orders` → `orders/`,  `*_trades` → `trades/`,
  `*_nbbo` → `nbbo/`,  `*_session` → `session/`,
  `*_orderbook`/`*_reference` → `reference/`,
  `*_par`/`*_participants` → `participants/`

Both `.csv` and `.parquet` are recognised. Use `--copy` to keep the
originals in place; `--dry-run` to preview without moving anything.

If you skip this step and `run.py` later detects loose raw files in
`data/`, it'll invoke `organize_raw.py` automatically (with a one-line
notice) before processing. Server-friendly — no prompts.

## 5. Exploratory data analysis (recommended)

Before processing, run the EDA report so you know what's there:

```
python eda.py                         # full report
python eda.py --dates 20240505        # restrict to one trade-date
python eda.py --tickers cba,bhp       # restrict to listed tickers
python eda.py --quick                 # file inventory only (no row scans)
```

The script scans `data/raw/` and prints eight sections:

1. **File inventory** — files per folder, sizes, csv/parquet pairing
2. **Tickers and dates** — filename-derived tickers + actual `TradeDate`
   values inside files (often differ from the date stamp in the filename)
3. **Orders breakdown** — total rows, order-type histogram, sweep count,
   sweeps that qualify for simulation, change-reason histogram, time range
4. **Trades breakdown** — total rows, deal-source histogram (lit / centre
   point / preference / APB), side distribution, time range
5. **NBBO coverage** — rows, distinct orderbookids, time range
6. **Session states** — distinct session names and types present
7. **Reference & participants** — security names, participant-type counts
8. **Cross-checks** — orphan files, csv/parquet pairing, schema family
   detection (`PascalCase (server)` vs `lowercase (local)`)

Use the report to confirm the date / ticker scope is what you expect, that
NBBO coverage is sufficient for simulation, and that orders and trades are
paired by filename.

## 6. Running the pipeline

There are two ways: a single command via `run.py`, or each stage individually.

### One command (recommended)

```
python run.py
```

This runs **process.py → aggregate.py → report.py** in sequence on
everything found in `data/raw/`. Filters are passed through:

```
python run.py --dates 20240505                           # one trade-date
python run.py --dates 20240505,20240905 --tickers cba    # date + ticker filter
python run.py --workers 4                                # tune parallelism
python run.py --skip-process                             # rerun reports only
```

Use `python run.py --help` for the full option list.

### Per-stage (for development)

```
python process.py   --dates 20240505 --tickers cba --workers 4
python aggregate.py --dates 20240505 --tickers cba --workers 4
python report.py                                              # whole-tree
python report.py    --dates 20240505                          # restrict
```

The same flags work on every stage that supports them. `report.py` only
takes `--dates`; the other two share the full filter set
(`--dates`, `--tickers`, `--orderbookids`, `--workers`).

## 7. Reading the outputs

After a successful run:

* **`data/reports/by_ticker.csv`** — one row per `(date, ticker)`, ~36
  averaged metrics per row. Best starting point.
* **`data/reports/by_day.csv`** — same metrics rolled up to date.
* **`data/reports/by_volume_bucket.csv`** — same metrics rolled up by
  quartile of order quantity (Q1–Q4).
* **`data/reports/per_security/{date}_{orderbookid}_{ticker}.csv`** — one
  row per sweep order.

Each row carries fill-quality columns (`qty_filled`, `fill_ratio`, `vwap`),
arrival-context columns (`arrival_midpoint`, `arrival_spread_bps`),
execution-cost columns (`exec_cost_arrival_bps`, `exec_cost_vw_bps`,
`slippage_bps`, `implementation_shortfall_bps`), timing columns
(`time_to_first_fill_sec`, `vw_exec_time_sec`), and market-context columns
(`market_drift_bps`, `avg_execution_spread_bps`).

## 8. Troubleshooting

* **"`python` is not recognised"** (Windows): the Python installer was
  run without the *Add Python to PATH* option. Reinstall and tick that box,
  or call Python through the launcher: `py -3.10 -m venv swp_env`.

* **"`Activate.ps1` cannot be loaded"** (PowerShell): see the
  `Set-ExecutionPolicy` workaround in section 3.

* **`No Centre Point orders found`**: the orders file does not contain any
  rows with `ordertype` in `{64, 256, 2048, 4096, 4098}`. Confirm the file
  was the right one for the date.

* **`Cannot compare: missing metrics files`** at the end of `aggregate.py`:
  Stage 2 produced zero simulated matches, so there is nothing to compare
  against. This is expected when the contra-order pool only contains
  ineligible order types (e.g. lit-only test data) and is not a code error.

* **`UserWarning: Could not infer format`** on parquet read: harmless;
  pandas falls back to mixed-format inference.

* **Permission errors writing to `data/processed/`**: make sure the venv
  user owns the project directory. On Windows, avoid running the project
  out of `Program Files` or any path with spaces and OneDrive sync.

```
python -m pytest tests/ -q
```
